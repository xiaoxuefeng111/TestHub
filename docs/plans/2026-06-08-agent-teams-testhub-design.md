# 通达信测试平台 Agent Teams 设计文档

## 背景

目标是在 SpectrAI 的 Agent Teams / 会话编排能力上，为当前仓库 `g:\Working\AI_Work\testhub_platform` 搭建一套可直接开工的多角色协作团队，用于完成开源项目的环境修复、后端修复、前端修复、数据库初始化与测试验证，并最终产出可运行项目与完整 `README.md`。

当前项目上下文（基于仓库扫描）：
- 后端：Python `requirements.txt`，核心框架为 Django 4.2
- 前端：`frontend/package.json`，Vue 3 + Vite
- 数据库：README 声明为 MySQL 8.0+
- 配置：存在 `.env` 与 `.env.example`
- 测试/自动化：Playwright、Selenium、Allure、Airtest 等依赖已出现在仓库中

## 设计目标

1. 建立 1 个 Team Lead + 5 个专业角色的团队模型
2. 团队创建后立即能对当前项目开工
3. 角色职责边界清晰，避免重复修改同一区域
4. Team Lead 统一协调跨模块问题，如环境变量、端口、CORS、数据库连接、前后端联调
5. 最终沉淀运行文档与测试验证结论

## 平台落地策略

由于当前 SpectrAI 内置工具已暴露：
- `create_standalone_session`
- `attach_session_to_team`
- `get_current_session_context`

但未直接暴露独立的 `create_team` 工具，因此采用以下落地方案：

### 推荐落地方式：Supervisor Team Lead 主导型

- 创建 1 个 `supervisor` 模式会话作为 Team Lead
- Team Lead 使用当前仓库目录作为工作目录
- Team Lead 在其上下文内继续拆解、派发和协调任务
- 如果创建后获得 `teamId`，则继续补建并挂接 5 个固定角色会话到同一 Team
- 如果未获得 `teamId`，则仍保持“Team Lead + 动态子 Agent”的可运行团队形态继续执行

这样既兼容当前平台能力，也能满足“立即开工”的要求。

## 团队结构

### 1. Team Lead（项目协调）
- 核心职责：拆解任务、分配给队友、合并结果、输出最终运行文档
- 工作范围：全仓库、全链路协调
- 关键 Prompt：

> 作为项目经理，你需要将用户提供的开源项目，拆解为环境、后端、前端、数据库、测试 5 个模块，分配给对应 Agent，并协调解决跨模块冲突，最终输出可运行的项目和完整的 README.md。

### 2. 环境配置 Agent
- 核心职责：依赖安装、版本兼容、环境变量配置、虚拟环境 / 容器化
- 工作范围：`requirements.txt`、`.env.example`、前后端依赖、启动前置条件
- 关键 Prompt：

> 你是环境配置专家，需根据项目依赖文件（package.json/requirements.txt 等），修复所有依赖安装问题，生成 `.env.example` 和完整的环境搭建步骤，确保项目基础环境可正常运行。

### 3. 后端服务 Agent
- 核心职责：后端报错修复、接口调试、服务启动配置、跨域处理
- 工作范围：Django 后端、API、CORS、服务启动
- 关键 Prompt：

> 你是后端开发专家，负责修复后端代码编译 / 运行报错，配置服务启动端口、跨域规则，确保后端服务可正常启动并响应基础请求。

### 4. 前端开发 Agent
- 核心职责：构建报错修复、页面渲染问题、静态资源路径、前后端联调
- 工作范围：Vue/Vite 前端、构建与页面渲染
- 关键 Prompt：

> 你是前端开发专家，负责修复前端构建报错、依赖版本冲突、页面渲染异常问题，确保前端项目可正常构建并访问。

### 5. 数据库 Agent
- 核心职责：数据库初始化、连接配置、SQL 脚本执行、数据验证
- 工作范围：MySQL 识别、初始化、迁移、连通性验证
- 关键 Prompt：

> 你是数据库专家，负责识别项目数据库类型与版本，编写初始化脚本，修复数据库连接问题，验证数据库与应用的连通性。

### 6. 测试验证 Agent
- 核心职责：全流程冒烟测试、问题定位、二次修复反馈
- 工作范围：后端接口、前端页面、联调、最终测试报告
- 关键 Prompt：

> 你是测试工程师，按用户场景执行完整的项目启动流程，验证核心功能是否正常，标记所有问题并反馈给对应 Agent 修复，输出最终测试报告。

## 工具权限映射

结合平台当前能力，权限以“职责允许调用的工具类型”表达，而不做底层强隔离承诺：

- Team Lead：全权限，可读仓库、查看文档、创建/协调子会话、汇总结果
- 环境配置 Agent：依赖安装、读取配置、修改配置文件、生成环境说明
- 后端服务 Agent：读写后端代码、运行后端命令、检查 API 与 CORS
- 前端开发 Agent：读写前端代码、运行前端构建/启动命令、检查页面资源与接口地址
- 数据库 Agent：修改数据库相关配置、编写初始化脚本、验证数据库连接
- 测试验证 Agent：执行启动命令、访问接口/页面、汇总问题与测试报告

## 执行流程设计

### 阶段 1：Team Lead 建立上下文
1. 扫描仓库结构、README、依赖文件
2. 输出任务拆解清单
3. 标注跨模块风险

### 阶段 2：专业角色并行推进
1. 环境配置 Agent 修复依赖与环境变量问题
2. 后端服务 Agent 修复 Django 启动与接口问题
3. 前端开发 Agent 修复构建与联调问题
4. 数据库 Agent 识别 MySQL 配置并修复初始化链路

### 阶段 3：集成与回归
1. 测试验证 Agent 执行全流程冒烟
2. 问题回流给对应角色
3. Team Lead 汇总修复结果并做最终收敛

### 阶段 4：交付
1. 输出可运行结论
2. 更新或补充 `README.md`
3. 输出最终测试报告

## 跨模块冲突协调规则

1. `.env` / `.env.example` 由环境配置 Agent 主责，其他 Agent 不主动覆盖
2. 数据库连接串由数据库 Agent 主责，后端 Agent 仅消费协商后的配置
3. API 基础地址、代理、跨域由前后端 Agent 与 Team Lead 共同确认
4. 测试 Agent 不直接做大规模功能改动，只做验证和问题回流；必要修复需回到对应专业角色
5. Team Lead 负责最终合并规则与完成标准判定

## 风险与应对

### 风险 1：平台未直接暴露 create_team
- 应对：使用 `supervisor` 会话作为可运行团队入口

### 风险 2：仓库已有大量未提交改动
- 应对：当前先做团队创建与会话编排，不自动提交代码或文档，避免污染用户现有工作区

### 风险 3：编码或历史文件状态不一致
- 应对：文本修改统一走平台文件工具，减少 Windows 编码问题

### 风险 4：本机缺少 MySQL / Node / Python / 浏览器依赖
- 应对：由环境 Agent 与数据库 Agent 先探测并生成缺失项清单，再决定本地修复顺序

## 完成标准

- Team Lead 会话已创建并可直接工作
- 团队角色职责与 Prompt 已固定
- 团队已开始针对当前仓库执行任务
- 后续执行目标明确：
  - 后端可启动
  - 前端可构建并访问
  - 数据库配置清晰且可验证
  - 具备完整 README 与测试报告
